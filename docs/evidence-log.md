## D20 — Start placement retry (23 Nov)
gradual-s12 failed at start: JuPedSim's random placement fitted only 1498 of 1500 people (0.6 m spacing). `place()` in `sim/run_sim.py` now retries with seed + 1000, + 2000, ... ## D21 — Live mode over MQTT (23 Nov)
- The twin loop in `twin/run_twin.py` is now a `Twin` class that takes one report at a time. The offline `run()` uses it, so the experiments and live mode share the same code. Checked: identical estimates, forecasts, alerts and blind alerts before/after on gradual-s04, surge-s05 (phones, option B, failure test), ingress-s03 and the full-observability baseline.
- `live/`: each sensor is its own MQTT client with a retained status and a Last Will (a failed sensor drops its connection, so the broker announces it offline). The twin service processes reports in order on the event clock: when every online sensor has reported, when a later report arrives, or 80 % of a report interval after it was due (at most 2 s). Missing sensors are NaN, so the twin keeps stepping when everything goes quiet. Sensors start once the twin's retained status is online.
- Live alerts equal the offline ones for the same seed (gradual-s04, surge-s05 with option B and failures, surge-s05 entrance_exit with failures, ingress-s03).
- Latency on the sandbox (same machine, Mosquitto 2): Nagle's algorithm added ~40 ms per message, so both broker configs set `set_tcp_nodelay true`. After that, a report with every sensor in takes ~30 ms from the last sensor message to the state arriving at the logger, of which ~27 ms is the twin (EnKF update + 120 s forecast, 100 members). A report with a lost message waits for the deadline.
- Windows application control on our PC blocks mosquitto.exe, so `live/broker.py` runs a pure-Python broker (amqtt) for local tests. Same alerts on the failure demo, median latency ~30 ms. amqtt redelivered the twin's own last retained message to it on reconnect, so the twin and logger now ignore topics that aren't theirs.
- Schemas: sensor ids are now C## (the venue's mounting spots), count messages carry `sent_at` (latency only) and the option B `sketch`; new `twin_state` and `twin_alert` schemas; `tests/live/test_messages.py` validates them.

## D22 — Simulation validity rule (23 Nov, before any twin results on the new runs)
Two of the 10 blockage runs jammed in the simulator: blockage-s10 stopped at 386 s with 781 of 1,100 people still inside, blockage-s07 with 116. This is the velocity model's known clogging (Xu, Chraibi & Seyfried, 2021), not an event we want to test the twin on. Rule, applied to every scenario and both venues: a run counts only if at least 95 % of the crowd gets out (or in); a run that fails is replaced by the next seed (13, 14, ...). `sim.scenarios.test_seeds()` gives the seeds in use, `run_all` simulates replacements automatically and lists the runs it left out. Retuning the gridlock breaker instead was rejected: it changes every run and earlier attempts made things worse (D3).

## D23 — Venue 2 (festival hall) plugged in (23 Nov)
- Layout by our teammate (11 zones, 1,652 m², a 96 m² entry queue with a 2 m ticket checkpoint, a bar, two 2 m exit gates, 21 sensor spots). We kept her geometry, sensor spots and thresholds and added the v1.3 fields our code reads (exit areas, gates, entrance with checkpoint, presets, risk zones Z01/Z06/Z09). Her separate simulator and twin (`venue2/` in her zip, from an older repo version) were not used: different twin, cut-off 0.7 and alert matching, so not comparable.
- Code: the active venue is chosen with `CROWDTWIN_VENUE` (default concert venue); venue 2 data lives in `data/venues/festival_hall_v2/`. The simulator handles several gates (everyone uses the nearest one) and an entry checkpoint (arrivals line up in front of it, pass through, then walk to their spot); the twin's zone model has an exit for every exit area; calibration measures the flow through every gate. Concert venue runs are byte-identical before/after (blockage-s05, counterflow-s06, ingress-s03).
- Scenarios: normal (800), gradual and surge (1,500), and ingress (1,500; 70 % arrive in the first 150 s, over twice what the checkpoint passes).
- First runs (sandbox): the checkpoint passes ~3 people/s (1.5 p/m/s). The entry queue fills Z01 to ~3.2–3.4 p/m² on average (amber) for about 4 minutes, not red: the queue is a wedge pointing at the checkpoint (locally ~4.5 p/m²) and the corners of the pen beside the door stay empty. In egress the two queues form in the 600 m² audience zone in front of each gate, so no zone reaches red either (approach zones ~2 p/m²). Walking straight at the checkpoint gave red, but only because people got pinned on its corners (47 still stuck at the end), so we fixed that rather than keep it.

## D24 — How venue 2 is evaluated (23 Nov, before any twin results on venue 2)
- No zone reaches red in venue 2 (D23), so the red detection rate is undefined there. Venue 2 is scored on: amber warnings (detection rate, lead time, false alarms, with bootstrap intervals over runs), red alerts (every one is a false alarm) and density error (MAE, sensed and unsensed zones).
- Small grid: every scenario (normal, gradual, surge, ingress) on test seeds 3–12, medium noise, 4 sensors, all four placements, phones and tags, options A and B, plus the full-observability, sensor-only and trend baselines (`run_experiments small`).
- Calibration as for the concert venue (seeds 1–2: capacity through both gates, storage densities, turning, priors, observation model), except the alert cut-off tau, which is taken from the concert venue: it is part of the method, and venue 2's calibration runs have no red events to choose it on.
- Checked on venue 2's calibration runs only (seeds 1–2), never its test seeds. The twin forecasts red in the entry pen (Z01) now and then during the door rush: its model lets every arriving person into Z01, while the simulation makes them wait outside once the pen is full, so Z01 never reaches red in the truth and these alerts count as false alarms. In words: more people want in than fit at a safe density. We tried capping arrivals at the pen's storage density in the model; with phones the ensemble then sat at the cap with no spread and could not follow the queue down (MAE 0.07 -> 0.26), so we reverted it. The model is unchanged from the concert venue.
- Method frozen as of this entry: no twin or metric changes after seeing venue 2 test seeds or concert seeds 9–12.

## D25 — Demo dashboard (23 Nov; demo only, not in the paper)
- `live/dashboard.py` + `live/dashboard.html`: a one-page operator view in the browser, fed by the broker through server-sent events (Python standard library, no extra install). It shows the venue coloured by the twin's estimate or the true density, the simulated crowd, sensor ranges and status, the 2-minute risk per zone against tau, the alert log, a timeline of the selected zone (true density, twin estimate, P(red), alerts) and latency.
- The true density and positions come over the restricted `sim/{run}/truth` topic, which the publisher now sends as the `simulator` user and the dashboard reads as the `evaluator` (ACL updated); the twin still can't read it. The twin's state now lists the risk zones that are blind at that moment, so the map can mark them and unmark them when a sensor comes back.
- Every session is also saved as a single HTML file that replays the run in any browser (play, pause, speed, seek), as the fallback when the demo machine can't run Python or a broker. Checked: live and replayed views on surge-s05 with the failure test and on venue 2 arrivals, in headless Chrome, no page errors.
- `live/record.py` records several runs in one go; the dashboard opens arrivals on the entrance zone and egress on a risk zone away from it, and names failure-test recordings `dashboard_<run>-failure.html`.
- The live demo and recorder now use each run's own seed (as the experiments do) instead of seed 0, so a recording shows exactly the alerts of that run's row in the results (checked: gradual-s04 live = offline, red at 175 s in our sandbox data). With seed 0 every run shared the same message-loss pattern, which is why venue 2's two recordings both had a blind alert at 190 s.

## D26 — Docker packaging and the information-firewall test (24 Nov; artefact, not in the paper)
- `Dockerfile` + `docker-compose.yml`: the live demo runs with only Docker installed. Services: Eclipse Mosquitto with `broker/acl` and one login per component, the two dashboards (venue 1 on 8050, venue 2 on 8051), and on request the demo, the firewall check and the unit tests. `./data` is mounted, so recordings and latency logs land on the host.
- Why: on our Windows machine Application Control blocks `mosquitto.exe`, so the live runs used the Python broker (no ACL) and the information firewall was only described, never exercised. In the container the twin logs in as `twin` and the broker enforces the topic rules.
- `live/check_acl.py` tests the firewall on a running broker: the twin receives sensor counts but no `sim/#` truth, the evaluator receives both, a sensor cannot publish fake truth, and a client without a login is refused. All five pass in our sandbox Mosquitto with the same config the container writes; a wrong password fails with a clear message.
- `live/demo.py`: `--password` gives each part its own user; a missing run is simulated first (about 2.5 min); if the twin crashes the demo stops instead of leaving the sensors waiting (found while testing: the twin needed the calibration trajectories, which a fresh clone doesn't have).
- The fitted observation model is now saved with the results (`data/results/observation/{mode}_{noise}.npz`, same numbers as fitting on the fly, checked equal) so the twin runs without the calibration runs. Fresh-clone test (results folder only): demo on surge-s05 simulated the run, then live red at 320 s, 131 reports, median end-to-end 39 ms; 14/14 tests pass.
- Determinism: simulating gradual-s04 from scratch in our Linux sandbox gave a byte-identical trajectory file to the sandbox's earlier run of the same seed (same MD5). Our paper results were simulated on Windows, where floating point can differ slightly (technical report, section 18).
- JuPedSim only ships x86-64 Linux wheels, so the image is `linux/amd64` (emulated on Apple silicon).
- First run on our Windows PC with Docker Desktop: demo, firewall check (5/5 PASS) and tests (14/14) all worked, live median end-to-end 27.8 ms (95th 450 ms: the reports where one sensor message was lost, so the twin waits for the deadline, 0.8 x 5 s / speed = 0.4 s at speed 10; checked: 17 such reports, median 439 ms, the other 95 median 36 ms, same natively), but both dashboards stayed empty. Cause: the venue 1 and venue 2 dashboards used the same MQTT client id, so the broker kept closing one when the other connected, and after the reconnect neither had its subscriptions. Fixed with one client id per venue and subscribing again on every connect; checked with both dashboards on one broker and a run per venue (no more "already connected" in the broker log, both pages fill).
- The dashboards now get the true crowd and densities every second instead of every 5 s, so the crowd moves smoothly; the sensors and the twin still work every 5 s, as in the method (checked: same alerts as before, red at 175 s on gradual-s04 in our sandbox data). Recordings grow from about 1 to 5 MB.
- Per-second dots still jumped, so the truth message also carries each person's id and the page moves every person from the previous frame to the newest one between messages (shown one second behind, at the screen's frame rate). Works the same live and in recordings; older recordings without ids just jump each second. Checked in headless Chrome, live at speed 2 and on a recording: no page errors, positions change between messages. Recordings about 7 MB.
- A demo started when the broker was not up failed with "Name or service not known" for `broker`. The broker now has a health check (a component user can log in) and restarts unless stopped, and every app container waits for it to be healthy before starting. The broker and dashboard ports are bound to 127.0.0.1, so only the computer running Docker can reach them.
- The first image was 2.5 GB. Most of it was PySide6 and VTK (about 1.2 GB installed), which JuPedSim lists as dependencies for its viewer; the simulation never imports them. The image now installs JuPedSim without its dependencies. Checked in an environment without PySide6 and VTK: tests 14/14, gradual-s04 simulated from scratch byte-identical to the earlier sandbox run (same MD5), live demo same alerts (red at 175 s). `.dockerignore` also leaves out everything in `data/` except the paper results (the folder is mounted at run time).
